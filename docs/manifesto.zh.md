# 无守护进程的手柄映射——一份理念宣言

主流手柄映射方案（DS4Windows、x360ce、reWASD、Steam Input）都遵循同一套架构：**常驻程序**。一个后台进程 7×24 小时运行，创建虚拟手柄设备，让所有游戏"以为"接到的是虚拟手柄。这套方案能用，但代价是：

- 托盘图标永远挂着，内存和 CPU 永远被占用；
- 通常需要内核级虚拟总线驱动（ViGEm 等），安装麻烦、Windows 更新易碎、天然招致反作弊警觉；
- 全局设备接管——映射器拦截的是*所有*手柄流量，哪怕某些应用根本不想要它。

**adf-gamepad-modder 反其道而行。** 映射器是一个极小的 DLL（`winmm.dll` / `version.dll` / `dinput8.dll` 代理），通过标准的 DLL 搜索顺序部署，**加载进游戏进程自己内部**。它在游戏进程里用 SDL3 轮询物理手柄，再通过 `SendInput` 在用户态注入合成的键鼠输入。游戏退出，映射器随之消失。系统里没有安装任何东西，后台没有运行任何东西，其他任何程序不受任何影响。

| | 常驻式映射器 | adf-gamepad-modder |
|---|---|---|
| 后台进程 | 永远运行 | 无——随游戏生灭 |
| 内核/虚拟驱动 | 通常需要 | 从不 |
| 全局副作用 | 设备接管 | 零（按游戏逐个启用） |
| 老游戏兼容（DirectInput 轮询、RawInput） | 视实现而定 | 为此而设计 |
| 部署 | 安装 + 自启动 | 4 个文件放进游戏目录 |

## 为什么这个概念值得推广

1. **更少的系统侵入**：不装驱动、不留进程，用完即走，符合"工具应当隐形"的直觉。
2. **天然按游戏隔离**：每个游戏目录放一套，配置跟着游戏走，换游戏零切换成本，也不会误伤其他应用。
3. **老游戏友好**：映射代码与游戏同进程，DirectInput 轮询时序、扩展扫描码、相对鼠标这些老游戏敏感的细节，都在同一时钟域内解决。
4. **架构上更简单**：一个 C++20 静态核心 + 一份 JSON，没有 IPC、没有驱动、没有服务。

## 许可与态度

代码采用 Apache-2.0：**你可以自由使用、修改、闭源商用**。这个概念——进程内、无守护的手柄映射——明确欢迎被任何人复制、重写、发布到任何产品里。这正是本仓库存在的意义。

唯一请求：不要把它用于联机竞技游戏的作弊。它也不提供任何隐身功能——代理 DLL 明晃晃躺在游戏目录里。
